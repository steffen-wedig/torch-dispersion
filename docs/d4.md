# DFT-D4 in torch-dispersion

`torch_dispersion.d4.d4_dispersion` evaluates the full DFT-D4 dispersion energy, forces and stress for
molecules and fully periodic cells. It is the dftd4 4.3.0 `d4` model with EEQ-2019 charges and
rational (Becke–Johnson) damping, for both the two-body term and the ATM term. The oracle is the
pinned PyPI package `dftd4==4.3.0`. It agrees to 1e-17 Hartree in energy, 1e-18 Hartree/bohr in
molecular gradients and 1e-16 Hartree in virials, and periodic gradients pass the 1e-9
Hartree/bohr test tolerance. Do not compare against dftd4 < 4.1.1 (see
[Older dftd4 versions](#older-dftd4-versions-periodic-atm-gradient)).

```python
from torch_dispersion.calculators.ase import TorchD4Calculator
from torch_dispersion.d4 import d4_dispersion
from torch_dispersion.settings import D4Settings, NvalchemiNeighbors

settings = D4Settings.from_functional("r2scan", neighbor_backend=NvalchemiNeighbors())
result = d4_dispersion(numbers, positions, cell, pbc=True, settings=settings, charge=0.0)
result.energy, result.forces, result.stress, result.charges
atoms.calc = TorchD4Calculator(settings, charge=0.0)
```

The damping parameters are the functional's `d4.bj-eeq-atm` entry in dftd4's
`parameters.toml`; `s6 = 1`, `s9 = 1` and `alp = 16` are the defaults. Entries always set s8, a1
and a2; 31 of the 118 also set s6 and/or s9 (double hybrids, e.g. B2PLYP s6 = 0.64, and some 3c
methods). `D4Settings.from_functional(name, atm=True, **overrides)` reads a frozen copy of that
table (`src/torch_dispersion/d4/functionals.json`, written by
`scripts/export_d4_functionals.py` from dftd4 4.3.0; `D4Settings.functionals()` lists the
names):

- The name is matched case-insensitively and otherwise exactly, as
  `dftd4.parameters.get_damping_param` does (`r2scan-3c`, `wb97x-2008`, `pbe0_2`). An unknown
  name raises `ValueError` with the list of names.
- The merge order is defaults → entry → `atm=False` (s9 = 0, so the ATM term and its neighbour
  list are skipped) → `overrides`. The overrides set any other field, e.g.
  `D4Settings.from_functional("pbe", atm=False, device="cpu", compile=False)`.
- dftd4 is not needed at runtime; the tests check every entry against
  `get_damping_param`.

The cutoffs default to
dftd4's: two-body 60 bohr, ATM 40 bohr, D4 CN 30 bohr. The EEQ CN range of 25 bohr is fixed,
because it is part of the EEQ-2019 model.

### ORCA's D4rev (wB97X-D4rev, wB97M-D4rev)

ORCA (6.0 and later) has the simple-input keywords `WB97X-D4REV` and `WB97M-D4REV`. D4rev is
not a different dispersion model: it is the same `d4` model (EEQ-2019 charges, BJ two-body,
ATM with s9 = 1) with revised damping parameters. dftd4 ships the same numbers under the names
`wb97x-rev` and `wb97m-rev`:

```python
settings = D4Settings.from_functional("wb97m-rev")  # wB97M-D4rev, ATM on as in ORCA
```

| ORCA keyword | name here | s6 | s8 | a1 | a2 | s9 | source |
|---|---|---|---|---|---|---|---|
| `WB97X-D4REV` | `wb97x-rev` | 1.0 | 0.4485 | 0.3306 | 4.279 | 1.0 | doi 10.1063/5.0133026 |
| `WB97M-D4REV` | `wb97m-rev` | 1.0 | 0.842 | 0.359 | 4.668 | 1.0 | doi 10.1021/acs.jctc.3c00717 |

The parameters are those of the ORCA 6.1.1 manual, section 3.4.1.7, Table 3.15. ORCA lists
no `alp`; dftd4's default of 16 applies, as for every D4 functional. `tests/test_d4_rev.py`
checks the table against ORCA's numbers literally. It also checks energy, gradient and virial
against dftd4 4.3.0, which looks the parameters up by name in its own Fortran table. The cases
are molecules and the two ions, ATM on and off, an 80-atom cluster of 21 elements up to Pt
(neutral and +2), the fixture crystals (short cutoffs; default cutoffs as `slow`), compiled
kernels, CUDA and a TorchSim batch of molecules. All agree within the D4 tolerances (1e-10
Hartree, 1e-9 Hartree/bohr). In practice the agreement is 1e-15 eV on small molecules.

`scripts/benchmark_d4rev.py` repeats the comparison on molecular batches. On 250-atom
clusters dftd4 differs by up to 1e-9 eV in energy and 1e-8 eV/Å in forces. That comes from
dftd4's EEQ solve, not from this code: its charges leave a residual of ~1e-9 in the EEQ
equations of those clusters (cond(A) ≈ 90), against ~1e-13 for torch-dispersion (see the note
on dftd4 4.3.0's EEQ precision below).

ORCA itself was not run (no installation was available when this was written). The match to
ORCA therefore rests on ORCA's D4 being dftd4's model with the same reference data, charges
and cutoffs. A direct check against ORCA's printed dispersion energy and gradient for a
`! wB97M-D4rev` run is still open.

## TorchSim model (batched)

`torch_dispersion.calculators.torchsim.D4Model(settings)` is a TorchSim `ModelInterface`. It needs the
optional extra (`uv sync --extra torchsim`, or `pip install "torch-dispersion[torchsim]"`). The
package's top-level import does not load torch-sim; only `from torch_dispersion.calculators.torchsim import
D4Model` does.

```python
import torch_sim as ts
from torch_sim.models.interface import SumModel
from torch_dispersion.calculators.torchsim import D4Model
from torch_dispersion.settings import D4Settings

d4 = D4Model(
    D4Settings(
        s8=0.60187490, a1=0.51559235, a2=5.77342911, s9=0.0, neighbor_backend={"kind": "nvalchemi"}
    )
)
model = SumModel(mlip, d4)  # mlip: any float64 ModelInterface on the same device
final = ts.optimize(
    system=atoms_list,
    model=model,
    optimizer=ts.Optimizer.lbfgs,
    init_kwargs={"cell_filter": ts.CellFilter.frechet},
    autobatcher=True,
)
```

**Outputs** (float64 by default, detached; `positions.requires_grad` is not needed):

- `energy` (S,) eV;
- `forces` (N, 3) eV/Å;
- `stress` (S, 3, 3) eV/Å³ = sym(dE/dε)/V, the ASE and TorchSim sign convention (as
  `D4Result.stress`). Periodic batches only: a batch of molecules returns no `stress`;
- `charges` (N,) EEQ partial charges, only with `D4Model(settings, compute_charges=True)`.

Each system's total charge is the state's `total_charge` (or `charge`) per-system extra, or 0
(e.g. `ts.io.atoms_to_state(atoms, device, dtype, system_extras_map={"total_charge":
"charge"})` reads `atoms.info["charge"]`). For the autobatcher, `memory_scales_with` is
`"n_atoms_x_density"`, since the 60 bohr two-body list (and the 40 bohr ATM list if s9 ≠ 0)
dominates memory. `compute_forces` and `compute_stress` are constructor arguments and settable.

**Design.** The batch goes to `torch_dispersion.d4.d4_dispersion_batched` (usable without
torch-sim), and every stage runs on the whole batch at once. `d4_dispersion` is the same code
path with a batch of one, so the dftd4 oracle tests exercise it directly.

- **Neighbour list:** one flat list over all atoms with global indices, from one
  `system_idx`-aware nvalchemiops call (the brute-force backend builds per system and
  concatenates). Each row takes the cell of its system. The list is stored compactly (int32
  indices, int8 shifts: 8 bytes per entry) and is never expanded as a whole: restriction to the
  shorter cutoffs and the coincidence check work in row chunks.
- **EEQ:** the Wigner–Seitz image pairs and the direct Ewald sum run over one flat list of the
  image pairs of all systems, each with its own cell and splitting α (the α bisection runs on
  the host for all cells after one transfer). The Coulomb matrices are assembled padded to the
  largest system, (S, n_max, n_max), with empty rows decoupled (unit diagonal, q = 0), and all
  bordered systems are solved by one batched `torch.linalg.solve` with the per-system total
  charges. The direct sum has a hand-written backward.
- **Graph stage:** CN on the flat list, the EEQ charges, the weights and C6(q), C6(0) as
  per-system blocks (S, n_max, n_max) (one batched W C6_ref Wᵀ) are one function, compiled with
  dynamic shapes, so its backward is one compiled graph too.
- **Two-body term:** one tile loop over all atoms of the batch, `pair_block_size` (512)
  centres × `pair_tile_size` (4096) neighbours per call. The pair kernel cuts each tile from the
  list when it uses it, builds the tile's displacement vectors from the positions, indices,
  shifts and the centre's cell (written out as 3-term sums, so they fuse into the kernel),
  reads C6_ij from the flattened blocks at (system, local i, local j), and accumulates energy
  and virial per system. The force on a centre is −2 × its row sum of dE/dv: the list is full
  and symmetric (the partner (j, i, −T) of every pair carries the opposite dE/dv), so nothing is
  scattered to the neighbours.
- **ATM term** (s9 ≠ 0): one tile loop over all atoms of the batch as well (`atm/flat.py`),
  `centre_block_size` (32) centres × a tile pair of the 40 bohr list per call. The kernel builds
  the centre legs from positions, shifts and the centre's cell, and reads C6_ij, C6_ik and the
  far side's C6_jk from the flattened C6(0) blocks, which works because all three atoms lie in
  the centre's system. Gradients use the pair identity of
  [`atm_pair_gradients.md`](notes/atm_pair_gradients.md): 3/2 × the centre-leg derivatives is exact,
  so the far side needs none. Forces are −2 × row sums, as in the two-body kernel, and dE/dC6
  is a scatter-add of B·T entries per tile. Each centre block gets its own tile width: the
  smallest power of two × `min_neighbor_tile_size` (32) that holds its longest list, at most
  `neighbor_tile_size` (512). A block of 15-atom molecules then runs (32, 32, 32) tiles
  instead of (32, 512, 512).
- **One `autograd.grad` for the batch**, with one strain leaf per system.

Consequences:

- **Results equal `d4_dispersion` on each system to rounding**, not bit for bit: the batch
  solves each system's EEQ inside a matrix padded to the largest system (a different LU), and
  on CUDA the scatter-adds are atomic. The charges amplify rounding strongly (1-ulp noise in the
  EEQ matrix of a 1024-atom box moves them by ~3e-12 e), so the tests compare charges at 1e-10 e
  and forces at 1e-12 eV/Å.
- **No recompilation for new batches:** the graph stage has dynamic shapes, the tile kernels
  fixed tile shapes, and the batch-dependent sizes (S, n_max, the species set) are not
  specialised on. Full-width ATM tiles (`neighbor_tile_size`) run a graph with a static
  width. All narrower widths share one graph in which the width is a dynamic dimension. A
  first version compiled one static graph per width: with the widths of the test suite, that
  exceeded dynamo's recompile limit of 8 per function, a hard error under `fullgraph=True`. A
  version with only the dynamic graph was 1.7× slower on dense cells (8.4 s against 4.9 s for
  the 12 crystals below).
- **Memory is that of the whole batch.** The flat 60 bohr list costs 8 bytes per entry (about
  0.1–0.15 GiB per 1000 atoms of a molecular crystal), the EEQ and C6 blocks S n_max² entries each.

**Limitations.**

- **One periodicity per batch.** TorchSim states carry one `pbc` for the whole batch, and it
  must be all True (3D cells) or all False (molecules), like `d4_dispersion`. Mixed flags such as
  slabs raise `ValueError`.
- **The ATM term is compute-bound** on dense periodic cells at the default 40 bohr: a torch
  tile is (B, T, T) float64 work plus its reductions. That cost is now linear in the number of
  triangles, but a fused (Triton) kernel is the next step there.
- **Padding.** The list rows are padded to the widest row of the batch (in molecular crystals
  every atom of a cell has nearly the same count, so this is the densest cell's width), and the
  EEQ and C6 blocks to the largest system. Very uneven batches pay for that.
- **No `retain_graph`** (differentiable simulation): the outputs come from analytic kernels.
- **Atoms must be ordered by system**, as TorchSim's own states are.

## Definition (dftd4 4.3.0, multicharge 0.5.0, mctc-lib 0.6.1)

1. **D4 CN:** CN_i = Σ_j den_ij · ½ (1 + erf(−7.5 (r − Rc) / Rc)).
   - Rc = Rcov_i + Rcov_j, the D3 covalent radii scaled by 4/3.
   - den_ij = k4 exp(−(|EN_i − EN_j| + k5)² / k6), with Pauling electronegativities.
   - Hard cutoff.
2. **EEQ charges:** the bordered system [A 1; 1ᵀ 0] [q; λ] = [x; Q].
   - x_i = −χ_i + κ_i CN'_i / √(CN'_i + 1e-14).
   - CN' is the erf CN without the EN factor, 25 bohr, capped smoothly at 8 by
     log(1 + e⁸) − log(1 + e^(8 − CN)).
   - For molecules: A_ij = erf(r / √(σ_i² + σ_j²)) / r and A_ii = η_i + √(2/π) / σ_i.
   - For cells: multicharge's Ewald form, described next.
3. **Weights and C6:** w_ia = ζ_ia(q_i) · Σ_{g ≤ ngw_a} exp(−6g (CN_i − CN_a)²) / norm.
   - ζ(q) = exp(3 (1 − exp(2 η_i (1 − (q_a + Z_i) / (q + Z_i))))).
   - The norm-underflow fallback is one-hot on the reference with the largest CN.
   - C6_ij = Σ_ab w_ia w_jb C6_ab, where C6_ab is the trapezoid Casimir–Polder integral of the
     reference α(iω).
   - The two-body term uses the EEQ charges. The ATM term uses q = 0, as dftd4 does.
4. **Two-body term:** E2 = −½ Σ_{i,(j,T)} C6_ij (s6 / (r⁶ + R0⁶) + s8 rr / (r⁸ + R0⁸)), with
   rr = 3 r4r2_i r4r2_j and R0 = a1 √rr + a2.
5. **ATM term:** the same triangle sum as D3, with two changes.
   - The damping radius is the product of the three BJ radii R0_ij.
   - The exponent is alp / 3. D3 uses (alp + 2) / 3.
   - It reuses the D3 triple kernel (`torch_dispersion.atm.kernel`) unchanged.

### Periodic EEQ: replicated, not re-derived

multicharge does not use a converged Ewald sum. It truncates both sums at a fixed range:
- **Images:** every pair uses its Wigner–Seitz minimum images over the ±1 block of 27
  translations. Ties within 0.01 bohr² are averaged.
- **Direct sum:** erf(γr)/r − erf(αr)/r over a fixed 5 × 5 × 5 block of translations.
- **Reciprocal sum:** the 124 shortest G vectors of the 5 × 5 × 5 reciprocal block.
- **Splitting:** α comes from a bisection on the lattice (`get_alpha`) and is held fixed under
  strain.

The result depends on these truncations at roughly the 1e-8 level, so `d4/eeq.py` replicates
them. That includes two details that are easy to miss:

- **Wrapping:** dftd4's API wraps all positions into the central cell
  (`wrap_to_central_cell`, fractional [0, 1) with a 1e-14 tolerance) before building the
  model. The ±1 search finds minimum images only for wrapped positions. torch-dispersion searches on
  positions wrapped by the same rule and folds the wrap offsets into the image shifts, so the
  caller's (possibly unwrapped) positions stay the differentiable input.
- **Self-pair lookup:** for a self pair (i, i) multicharge skips the origin candidate and then
  indexes its translation table one entry too early. This is replicated too. Within the
  truncation it is harmless.

The reciprocal part is exactly periodic, so it factorises into structure factors, an N × 124
matmul. The direct part is evaluated in pair chunks, and its backward pass recomputes each chunk
under autograd, so memory stays bounded.

## Implementation

The structure is the same as the D3 ATM (`torch_dispersion.atm.realspace`, staged through
`torch_dispersion.core`):

1. **Graph stage:** positions and one strain per system → D4 CN and EEQ CN → charges → C6(q)
   and C6(0) blocks, for the whole batch (see the TorchSim section for the batched layout).
   - CN, the charges and both C6 are one function compiled with dynamic shapes; only the
     cell-dependent EEQ setup (α, image pairs) and the direct Ewald sum run outside it.
   - EEQ always runs in float64. The direct sum has a hand-written backward; the solve is
     differentiated by autograd through `torch.linalg.solve`.
2. **Blocked stage, on detached C6:**
   - The two-body kernel (`pairwise/rational.py`, shared with the D3 C6 test) evaluates
     `pair_block_size` centres × `pair_tile_size` neighbours per call, over all atoms of the
     batch, with analytic gradients: forces from row sums (pair symmetry), per-system energy
     and virial and dE/dC6 by scatter-add.
   - The ATM kernel (`atm/flat.py`) shares the per-triangle math of the D3 kernel
     (`atm/kernel.py`, `triangles` and `leg_derivatives`) with an R0 table of BJ radii, but
     runs over the whole batch with per-pair gradients (see the TorchSim section).
3. **Chain closure:** one `torch.autograd.grad` through both C6 adds the CN and charge
   contributions.

Reference tables are in `d4/reference_data.npz`, written by
`scripts/export_d4_reference_data.py`. The sources are tad-dftd4, tad-multicharge and tad-mctc.
- tad-multicharge stores the EEQ parameters, and tad-dftd4 builds r4r2, in float32. The export
  parses those literal values from the source text in float64.
- The reference α(iω) are evaluated in float64 with the default ga = 3, gc = 2.
- `tests/test_d4_data.py` checks CN, charges, C6 and polarisabilities against dftd4's
  `get_properties`. Against dftd4 4.1.0 every quantity agreed to ≤ 2e-14 relative.
- dftd4 4.3.0 solves the EEQ system less precisely. On the 28-atom all-element cluster its
  charges leave a residual of ~5e-12 in the EEQ equations (cond ≈ 50), against ~3e-15 for
  torch-dispersion. The test therefore compares charges at 1e-11 absolute, and the charge-scaled C6
  and polarisabilities at 1e-10 relative. The CN stays at 1e-12. Energies are unaffected at
  the 1e-10 Hartree tolerance.
- The error grows with the system size. On the fixture liquids cut out as ~250-atom clusters
  (cond(A) ≈ 90), dftd4's charges leave residuals of 8e-10 to 2e-9 and differ from
  torch-dispersion's by up to 3e-9 e, while torch-dispersion's residual stays at ≤ 2e-13. The
  energies still agree to 1e-11 Hartree.

## Older dftd4 versions: periodic ATM gradient

dftd4 up to 4.1.0 returned a wrong analytic gradient for the ATM term in periodic systems. In
`src/dftd4/damping/atm.f90`, `get_atm_dispersion_derivs` multiplied each triangle's energy, the
CN and charge derivatives and the virial by the counting factor `triple`, but added the position
gradient terms (`dGij`, `dGik`, `dGjk`) without it. `triple` is 1/2 or 1/6 only for triangles
through periodic images of one atom, so molecules, energies, virials and the two-body term were
unaffected. The periodic gradient was off by about 1e-6 Hartree/bohr on the fixture crystals.
torch-dispersion's gradient agreed with finite differences of dftd4 4.1.0's energy to 5e-14.

The bug was fixed upstream in dftd4/dftd4#359, released in 4.1.1. The energy definition did not
change between 4.1.0 and 4.3.0 at default settings: the reference tables are the same, and
mctc-lib 0.6.1 only adds Hessian helpers. torch-dispersion results are the same against either version,
except for that gradient. The tests pin `dftd4==4.3.0`.

## Oracle coverage

dftd4 4.3.0's Python API sets the real-space cutoffs with `set_realspace_cutoff(disp2, disp3,
cn, width2, width3)`. The CPU tests use shortened cutoffs for periodic cells
(`tests/test_d4_dispersion.py`). The default 40 bohr ATM cutoff on cells and the liquid boxes are
`slow` tests, meant for a GPU. dftd4's smoothing widths (`width2`, `width3`, 4.2.0 and later) are
not implemented in torch-dispersion; the default width of 0 means hard cutoffs, which is what
torch-dispersion uses. The CN and charge internals are only exposed through `get_properties`, at the
default cutoffs (`tests/test_d4_data.py`).
